# 問題収集・作問・添削ガイド

更新日：2026-11-08。問題の収集・新規作成・既存問題の添削を依頼されたら、作業前にこの資料を読む。新しい指摘を受けたら、基準と該当する問題データを一緒に更新する。

## 優先する作問方針

以下は、2026-11-08にユーザーから指定された基準である。

1. **問題文・問い方・正解・別解を一体で設計する。** 問題文にある語をつなぐだけで答えられる別解を許すと、意図した知識を問えない。略称を問いたい場合は、正式名称を提示して略称を明確に尋ね、正式名称は正解・別解・再回答候補に入れない。
2. **綴りや頭文字から答えを推測できる情報は、原則として後ろに置く。** 「○○の略で」や正式名称の英語表記を冒頭に出してしまわず、用途や特徴などの知識を要する手がかりを先に置く。正式名称から略称を答えさせること自体が目的の問題では、その目的が伝わる問い方にする。
3. **基本的な定義や有名な特徴だけで答えられる浅い問題は、問題集の半分以下にする。** 関連ジャンルのabc本戦データを実際に読み、題材の広さと知識の粒度を合わせる。文字数を増やしただけ、一般的な定義に年号を付けただけでは難度を上げたことにしない。
4. **前半は少しマイナーな情報、後半は答えを特定しやすい情報にする構成を積極的に使う。** 制作背景、具体的な作品・事例、別分野とのつながりなど、答えに直接結び付く知識を前振りにする。最後まで聞けば分かるが、前半で押すにはより深い知識が要る形を目指す。全問を難問にする必要はない。
5. **前振りから決め手へ進む構成は一例であり、全問の必須形式ではない。** ユーザーは「ずばり、ポルトガルの首都はどこでしょう？」のような短い一問一答も認めている。単純な定義、対比、直接的な知識、作品横断の同定などを混ぜ、文を長くすること自体を目的にしない。
6. **手がかりとなる名称に答えや答えの一部が含まれる場合は、その部分を `___` に置き換え、冒頭に「___には答えが入ります。」と付ける。** ユーザー指定の形は「___には答えが入ります。愛知県では毎年これのイベントである『世界___サミット』が開かれる、漫画やゲームなどの人物に扮し、衣装や小道具で姿を再現する活動は何でしょう？」である。読み上げ用文章では `___` を「ほにゃらら」とし、冒頭も「ほにゃららには答えが入ります。」とする。伏せ字を無言で読み飛ばさない。

例として、単に「漫画やゲームなどの人物に扮し、衣装や小道具で姿を再現する活動」を問うより、先に愛知県の「世界___サミット」という関連イベントの手がかりを置き、後半にその定義を置く構成が指定された。イベント名中の正解部分は伏せ、読み上げでも正解を言わないようにする。

CNNの問題は次の形を採用する。

> 画像認識の分野で広く使われている「畳み込みニューラルネットワーク」は、アルファベット3文字で何と略されるでしょう？

- 正解：`CNN`
- 別解・再回答候補：なし。正式名称や、その読みは加えない。
- アプリが行う大文字小文字・全角半角・前後空白の正規化は利用できる。これは別の解答概念を許すこととは区別する。

URLのような問題は、資源の所在やブラウザーでの用途を先に示し、「Uniform Resource Locator」を略すという手がかりを後方へ置く。正式名称は解説に回してもよい。

## ローカルのabc本戦からの観察

分析対象は、ローカルへ登録した問題集「abc本戦」の確認済みCSV `.wrangler/abc-normalized.csv` の800問。そのうち大ジャンル「科学」は126問、小ジャンル「情報科学」は12問。全文の構文・文字数を機械集計し、情報科学12問と他ジャンルから抽出した構文例を精読した。このデータに対する観察であり、大会全体の一般的な出題規則とは断定しない。

文字数はUnicodeコードポイント数で、句読点・空白・括弧内の読みも含む。全800問は最短33字、中央値58字、最長96字。中央付近の50%はおおむね51〜64字。情報科学12問は46〜82字、中央値60.5字。全800問が「でしょう？」で終わっていた。新規問題では**50〜80字程度を推敲の目安**とし、必要な限定や自然な日本語を優先する。数値は文字数制限として使わない。

| 参考にする特徴 | 根拠となる元問題の番号・題材 | 新規作問への生かし方 |
| --- | --- | --- |
| 身近な用途・具体例から概念へ進む | 27：Unityで使う言語、326：S3・EC2からクラウドサービス | 学術的な定義に加え、利用場面や代表例から答えを特定する手がかりを選ぶ。 |
| 人物・作品を複数の独立した特徴で限定する | 53：愛称と共同創業、424：モチーフと活動場所 | どちらも同じ答えを指す、確認済みの事実を組み合わせる。 |
| 対比で問う範囲を明確にする | 383：クラウドとの対比、70：さえずりとの対比 | 対になる概念が明確な場合に使う。前振りの概念と問う概念の取り違えを避ける。 |
| 役割・動作をまとめて短い概念名を問う | 565：一度の認証で複数システムを利用 | 製品名などの余計な情報がなくても一意になる場合は、短い定義でよい。 |
| 語義や名前の由来を補助的に使う | 136：防火壁、476：伝道師 | 用途や役割を先に示し、語義を後方の追加ヒントとして使う。由来の確認も必要。 |
| 具体的な例から共通する概念へ導く | 236：寄生する菌、518：溶液の性質 | 例だけから別の上位・下位概念にも答えられないか、末尾の分類を確認する。 |
| 文末で答えの種類・単位を指定する | 72：名字、333：2つの感染症、496：3文字の略語 | 人名・言語・方式・略称など、何を答えるかを最後までぶらさない。 |
| 不十分な回答と正解を分ける | 415：処理方式に対する「言語」、540：略称に対する説明語 | 正解・別解・再回答・不正解を区別し、新規問題では問い方との整合を取り直す。 |

元問題には、略称を問うのに正式名称を別解として登録しているものもある。**新規作問・添削では上記のユーザー指定を優先する。** また、元問題の説明の単純化や時点依存の表現を、そのまま新しい事実の根拠にはしない。内容の正確性は別途確認する。

900問の改稿時には、同じ800問から「漫画・アニメ・ゲーム」45問と「言葉」64問などを読み直した。作品・作者の同定だけでなく、作者の別作品やメディア展開、制作背景、具体的な用例や故事を手がかりにする問題が見られた。一方、80番の古文の活用形、436番のゲームの道具の数のように短く直接問うものもある。簡単な定義を長く言い換えるのでなく、題材の広さ、必要な知識、早い段階で特定するための手がかりを一体で検討する。

## 1問を組み立てる手順

1. **答えを先に決める。** 短い語句で答えられる対象を選び、既存問題の正解・別解と照合する。同じ正解を再出題する場合は、依頼に合う理由があることを確認する。
2. **何の知識を問うかを決める。** 名称の知識、用途からの同定、人物の業績、略称への変換など、出題意図を1つに絞る。
3. **事実を調べる。** 公式文書・技術標準・原論文・公的機関等を優先し、本文のどの手がかりを支える資料かを確認する。技術分野の記述は一次資料を使う。検索結果の見出しだけで未確認の事実を加えない。
4. **手がかりを並べる。** 利用場面・特徴・具体例などから入り、決め手となる限定、綴り・由来などの補助ヒント、問い掛けの順を検討する。強いヒントを機械的に末尾へ移すと不自然になる場合は文全体を書き直す。
5. **問い方を確定する。** 「何という言語」「誰」「何方式」「アルファベット3文字で」など、答えの対象・表記を明示する。
6. **別解を1つずつ審査する。** 問題文を見ながら、その表記で本当に問いに答えているかを確かめる。辞書に載る同義語を無条件に追加しない。
7. **音で聞いて推敲する。** 修飾のかかり先、読みが必要な固有名詞、数字、同音異義語を確認する。表示本文と読み上げ用文章に同じ手がかりを含める。
8. **100問等のまとまりでも確認する。** 定義だけの問題、略称への変換、特定分野に偏らないようにし、同じ事実の言い換えや隣接問題の露骨な答えの開示も見直す。

## 問題文を添削する観点

- **一意性**：条件をすべて満たす別の答えがないか。必要なら対象の種類、条件、文字数を加える。例えば「信頼性のある通信」だけでは複数の規約が当てはまるため、略称の文字数や確認済みの固有条件も使う。
- **知識が必要な手がかり**：冒頭の英語を頭文字にするだけ、提示語を接続するだけで正解できないか。略称変換そのものを問う問題は、その形式を明示する。
- **本文中の答え**：正解・別解そのものが、固有名詞や別の用語の一部として含まれていないかも見る。例えばPythonを問う際の番組名中の「パイソン」や、キューを問う際の「エンキュー」は、出題意図に応じて解説へ回し、ほかの確認済みの特徴から問う。
- **前振りと決め手**：各情報が同じ正解を指すか。長い前置きの後で別の対象を問う形や、特徴を並べるだけの冗長さを減らす。
- **事実の範囲**：「最初」「唯一」「必ず」「すべて」などの強い表現は根拠と適用範囲を確認する。例外条件を削って誤りにしない。
- **時間**：「近年」「昨年」「現在」を安易に使わず、必要なら年を明記する。名称・仕様が変わる話題には確認日を残す。
- **分類**：言語・プログラム・方式・組織・サービス・データ形式・装置を混同しない。
- **自然な読み上げ**：英語の正式名称や長い列挙を増やしすぎない。アプリは丸括弧と中身を読み上げから除くため、必須の限定は括弧内だけに入れない。
- **創作**：参考問題の構文や知識の粒度を参考にし、問題文の転載や固有名詞だけの差し替えで増やさない。

## 正解・別解・再回答候補

| 問い方・状況 | 扱い |
| --- | --- |
| 「アルファベット○文字」「何と略される」と明確に略称を問う | 指定された略称を正解にする。正式名称やカタカナ読みを自動的に別解へ入れない。CNNの問題は別解・再回答候補とも空欄。 |
| 表記を限定せず、概念名を問う | 同じ概念を指し、本文からの答えの抜き出しにもならない一般的な同義語・表記揺れを別解にできる。 |
| 人物を問う | 姓だけで十分か、同姓の人物との区別が必要かを検討する。読みや綴りの許容範囲も決める。 |
| より広い概念しか答えていない | 正確だが不足した回答に限り再回答候補を検討する。例：DDoSに対するDoS。完全な別の概念を救済する目的には使わない。 |
| 問いの対象が違う・提示済みの語を答えている | 正解にしない。別解や再回答候補の追加で、曖昧な問題文を補修しない。 |

アプリはNFKC、前後空白除去、英字の小文字化後に完全一致で判定する。ひらがな・カタカナ、内部空白、記号は自動では同一視されない。略称のみを正解にしても、システムの正規化により `cnn` / `ＣＮＮ` は `CNN` と一致する。別解を増やすための変更は不要。

## 納品前の確認

- 全問を人の観点で読み直し、問題文・答え・別解・再回答候補の組を確認する。文字列の検査は補助として使う。
- 各問に出典URL・確認日・短い解説を付ける。正式名称や追加知識は必要に応じて解説へ収める。
- 元の問題データやバックアップはGitへ追加しない。観察結果は元問題の番号と要約で示す。
- CSVの固定IDを保つ。添削で別問題の新規登録にならないよう、同じIDで更新できる状態にする。
- `shared/csv.ts` と `shared/model.ts` で実際に解析し、件数、エラー、列の往復、正解・別解と再回答候補の衝突を確認する。
- 問題集・CSV・読み上げ用文章・解説・添削記録の内容を揃える。本番への登録・公開は別の操作として依頼範囲を確認する。
